Points à surveiller

Le code Supabase original est conservé uniquement dans les logs ; il n’est pas envoyé au frontend.
GET /employees/:id renvoie actuellement 500 si aucun employé n’est trouvé, car maybeSingle() retourne data = null. Ce cas devrait probablement produire 404.
Une erreur 23505 lors d’un PUT ou d’une autre opération est classifiée en unknown avec un statut 500, malgré getEmployeeErrorStatus() qui prévoit 409.
La réponse publique est volontairement simplifiée en { error: message }, ce qui est correct pour ne pas exposer les détails SQL. Pour faciliter le frontend, on pourrait ajouter un type contrôlé :

{
  "error": "Cet email existe déjà. Utilisez un email unique.",
  "type": "constraint"
}

Cela permettrait au client de distinguer validation, constraint, network et unknown sans exposer les détails internes de Supabase.
